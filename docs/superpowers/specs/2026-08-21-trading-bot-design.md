# 주식 분석 자동매매 봇 — 설계 (Phase 1)

## 목표

[TradingAgents](https://github.com/TauricResearch/TradingAgents)(멀티에이전트 LLM 기반 주식 분석 프레임워크)를 docker로 실행하여 얻은 매매 결정을,
토스증권 공식 오픈API를 통해 완전자동으로 실주문까지 연결하는 시스템을 만든다.

**Phase 1 범위**: 미국주식(토스증권 해외주식), 소규모 종목(3~5개), 하루 1회 배치 실행, 로컬 PC 상시 운영.
국내주식 확장·클라우드 이전·반자동(승인) 모드는 이후 단계 과제(로드맵 참고).

## 핵심 결정 사항

| 항목 | 결정 |
|---|---|
| 매매 실행 방식 | 토스증권 공식 오픈API (보유 중) |
| 자동화 수준 | 완전자동 — 사람 승인 없이 즉시 주문 |
| 대상 시장 | 미국주식 (추후 국내 확장 예정) |
| 실행 주기 | 하루 1회 배치 (장 시작 전 분석 → 장중 주문) |
| 배포 환경 | 로컬 PC 상시 실행 (E:\MyProject) |
| LLM | Google Gemini 2.5 Flash 무료 티어 (LangChain 기반이라 교체 용이) |
| 감시 종목 수 | 소규모(3~5개)로 시작 |

## 아키텍처

Windows 작업 스케줄러가 하루 1회 파이썬 오케스트레이터(`main.py`)를 실행한다. TradingAgents는 docker-compose로 띄운
별도 컨테이너이며, 오케스트레이터가 이를 호출해 종목별 분석 결과를 받아온 뒤, 자체 리스크 엔진을 통과한 주문만
토스증권 오픈API로 실행한다. 상태는 로컬 SQLite 파일 하나에 기록하고, 결과는 텔레그램으로 알림한다.

```
[Windows 작업 스케줄러] → main.py
   ├─ 1. STOP 파일 체크 (킬스위치)
   ├─ 2. 토스 API: 계좌 상태 조회 (현금/보유종목/당일 손익)
   ├─ 3. 서킷브레이커 체크 (오늘 이미 발동됐으면 종료)
   ├─ 4. TradingAgents 컨테이너 실행 (종목별 분석 → BUY/SELL/HOLD)
   ├─ 5. 리스크 엔진 (한도 적용, 주문 필터/사이징)
   ├─ 6. 토스 API: 승인된 주문만 실행
   ├─ 7. SQLite에 전 과정 기록
   └─ 8. 텔레그램 요약 알림
```

단일 오케스트레이터 프로세스로 구성한 이유: 현재 규모(소규모 종목, 일 1배치, 1인 로컬 운영)에서 다중 서비스
(docker-compose 여러 컨테이너)나 이벤트 큐 아키텍처의 이점(독립 배포, 수평 확장)을 쓸 일이 없고, 오히려 장애
지점만 늘어난다. 종목 수가 커지거나 클라우드로 옮길 때 오케스트레이터 로직을 FastAPI 서비스로 감싸는 확장은
쉽다.

## 컴포넌트

| 컴포넌트 | 역할 |
|---|---|
| `docker-compose.yml` | TradingAgents 컨테이너 (TauricResearch 이미지, 종목 리스트를 입력받아 JSON 결정 출력) |
| `config.yaml` | 감시 종목, 리스크 한도, 실행 스케줄, 서킷브레이커 임계값 |
| `.env` (git 제외) | 토스 오픈API 키/시크릿, Gemini API 키, 텔레그램 봇 토큰 |
| `orchestrator/main.py` | 전체 파이프라인 순서 제어, 최상위 예외 처리 |
| `orchestrator/toss_client.py` | 토스 오픈API 얇은 래퍼: 잔고/보유종목/당일손익 조회, 주문 실행 |
| `orchestrator/risk_engine.py` | 순수 함수 모듈 — 결정 + 계좌상태 + 한도 → 승인된 주문 목록 |
| `orchestrator/state.py` | SQLite 접근 (당일 실행 여부, 서킷브레이커 상태, 이력) |
| `orchestrator/notifier.py` | 텔레그램 알림 |
| `STOP` 파일 | 존재 시 즉시 전체 자동매매 중단 (킬스위치) |

## 데이터 흐름

1. 스케줄러가 장 시작 전 시각(KST 기준)에 `main.py` 실행.
2. `STOP` 파일 존재 여부 확인 — 있으면 "매매 중단 상태" 알림만 보내고 종료.
3. 토스 API로 현재 계좌 상태(현금, 보유 종목, 당일 실현+평가 손익) 조회.
4. SQLite에서 오늘 서킷브레이커가 이미 발동됐는지 확인 — 발동됐으면 신규 주문 없이 종료.
5. 감시 종목별로 TradingAgents 컨테이너 실행 → BUY/SELL/HOLD 결정 수집. 종목 하나가 실패해도 나머지는 계속
   진행(로그만 남김). 단, 토스 API 자체의 인증/연결 실패는 전체 중단 대상(아래 에러 처리 참고).
6. 리스크 엔진에 결정 + 계좌 상태 + 설정 한도를 입력 → 승인/거부/사이징된 주문 목록 산출.
7. 승인된 주문만 토스 API로 실행.
8. 분석 결과·리스크 엔진 판단 사유·주문 결과를 SQLite에 기록.
9. 텔레그램으로 요약(분석 결과, 실행/거부된 주문, 당일 손익, 에러) 발송.

## 안전장치

완전자동 매매이므로 아래 안전장치는 모두 필수로 구현한다.

- **일일 손실 서킷브레이커**: 매 실행 시작 시 당일 손익률을 계산해 설정 임계값 초과 시 SQLite에 "오늘 발동됨"을
  기록하고, 이후 같은 날 재실행되어도 신규 주문을 전면 차단한다.
- **종목당/일일 매수 한도**: BUY 결정 금액을 `min(종목당 한도, 남은 일일 매수 예산)`으로 강제 캡. 초과분은
  주문하지 않고 사유를 로깅한다.
- **최대 동시 보유 종목 수**: 신규 종목 BUY 시 현재 보유 종목 수가 한도 이상이면 거부한다. 기존 보유 종목의
  추가매수·매도는 이 한도의 영향을 받지 않는다.
- **킬스위치**: 실행 최초 단계에서 `STOP` 파일 존재 여부를 확인한다. 있으면 분석·주문을 모두 건너뛰고 알림만
  보낸다. 사용자가 파일을 생성/삭제하는 것만으로 즉시 개입 가능하다.
- **중복 실행 방지**: SQLite에 "오늘 실행 완료" 마커를 저장한다. 스케줄러가 같은 날 두 번 트리거되어도 주문이
  중복 실행되지 않는다.
- **API 실패 처리**: 토스 API 호출은 최대 2회 재시도(타임아웃 포함) 후에도 실패하면 해당 주문을 건너뛰고
  알림을 보낸다. 주문 중복 위험을 피하기 위해 맹목적인 재주문은 하지 않는다.
- **드라이런 모드**: `--dry-run` 플래그로 전체 파이프라인을 실행하되 실제 주문 API만 호출하지 않고 "이런 주문이
  나갔을 것"을 로그·알림으로만 보여준다. 실거래 전환 전 최소 며칠은 이 모드로 검증하는 것을 권장한다.

## 테스트

리스크 엔진은 실제 돈이 걸린 핵심 로직이므로 `tests/test_risk_engine.py`에 assert 기반 최소 테스트를 둔다:
종목당 한도 적용, 일일 예산 캡, 서킷브레이커 발동 시 전체 차단, 최대 종목 수 초과 거부, 킬스위치 동작. 외부
API(토스증권, TradingAgents)는 단위테스트 대상이 아니라 드라이런 모드로 검증한다.

## 알려진 리스크

- **로컬 PC 상시 운영**: 미국장 장시간은 한국 기준 야간~새벽이라, PC가 꺼지거나 네트워크가 끊기면 그 시점의
  주문·모니터링이 누락될 수 있다. Windows 작업 스케줄러에 "누락된 실행 시 로그온 시 즉시 실행" 옵션을 켜두고,
  기동 시 및 실행 직후 텔레그램으로 "정상 실행됨" 하트비트를 보내 무응답을 빠르게 감지하도록 한다.
- **무료 LLM 티어**: Gemini 무료 티어는 속도제한이 있어 종목 수가 늘어나면 한도를 초과할 수 있다. 위의 안전장치
  (금액 한도, 서킷브레이커, 킬스위치)가 판단 품질 저하로 인한 피해를 제한하는 역할을 겸한다.
- **토스 오픈API 세부 사양**: 해외주식 프로그램 매매 엔드포인트/인증 방식은 구현 단계에서 실제 API 문서로
  확인이 필요하다. 이 설계는 "계좌 조회 + 주문 실행"이 API로 가능하다는 전제 위에 있다.
